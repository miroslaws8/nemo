# Example app — build the Asset Zoo fixture (AI generation test)

Tests asset GENERATION: creates ONE blank course and AI-generates a batch of asset types into
it (with_ai:true), **5 assets per page**, then waits for every generation to finish and writes
a manifest mapping `asset type -> { page_id, asset_id, generation_status, learner_url }`.
`qa-asset-render <type>` reads that manifest to open the exact page and verify each asset.

The heavy, many-call flow is a Playwright script (`scripts/build-asset-zoo.mjs`) talking to the
API directly (same-origin fetch with the logged-in token). Your job: run it and interpret
output. Do NOT drive the browser yourself.

First batch = the 10 simplest (content/layout) types: text_block, content_block, hero, cards,
feature_grid, accordion, case_study, goals, numbered_grid, comparison_columns. Topic for
generation context = "Workplace fire safety for new employees" (blank course has no theme, so
the topic is passed as the prompt). Expand the `BATCH` list in the script later.

**Creates data on every environment, prod included:** ONE course per run (titled `[SMOKE] Asset Zoo <date>`), LEFT in place: it IS the fixture (remove old ones by the `[SMOKE] Asset Zoo` title). Title what you create as the shared contract says (Titles of what you create), and never delete anything yourself.

**Spends AI credits** on the environment it runs on.

## Setup
First run `cat ~/.hermes/qa-shared.md` in the terminal (there is no `read_file` tool here) and follow it: environments, the vault login, test data, browser mechanics, screenshots, marking what is wrong.
Arguments: the environment (`local`, `staging` or `prod`; default `staging`).
Any other words are a note from whoever started the skill: follow it within this skill's rules.

- Every non-manual type is generated with `with_ai:true` (dispatches generation jobs on the backend).
- `manual_only` types (from `GET /api/common/asset-config`) can't be AI-generated — the script adds them with `with_ai:false` and marks them `ai:false` in the manifest.
- `NO_AI=1` builds the cheap render-only variant (all `with_ai:false`, sample content).
- **Publishes the fixture**: a DRAFT course's learner view redirects to a "not published" page, so the build publishes the course at the end (`POST /api/instances/alias/:alias/courses/:course_id/publish`) — required for `qa-asset-render` to reach the assets. This is a `[SMOKE]` test course on this env, not assigned to real learners (distinct from "publishing to real learners", which stays banned).
- `ZOO_PUBLISH_ONLY=<hub_id>` publishes an EXISTING fixture course and exits (no rebuild, no new credits) — use it if a fixture was built before the publish step existed.
- `ZOO_REFRESH=<hub_id>` re-reads the course's page hashes and rewrites the manifest's `view_url`/`learner_url` with them (no rebuild) — the route addresses pages by HASH, not the numeric page_id, so the manifest URLs must use the hash.
- `ZOO_BLANK_ONLY=1` creates a FRESH blank course with ONE empty page and prints its EDIT url (`ZOO_RESULT={…edit_url…}`, also saved to `~/.hermes/asset-add-<env>.json`), then exits — no AI, no asset adds, no publish, no credits. This is the setup step for `qa-asset-add` (the agent-driven FRONTEND add test, which then adds assets through the real UI buttons).

## Credentials / alias

`QA_<ENV>_EMAIL` / `QA_<ENV>_PASSWORD` (STAGE|LOCAL|PROD) in `~/.hermes/.env`. Tenant alias is guessed from the host's first label; override `QA_<ENV>_ALIAS`. The API host is auto-captured from app traffic; override `QA_<ENV>_API` if needed.

## One-time setup (only if deps are missing)

```
cd ~/.hermes/skills/qa-asset-zoo/scripts && pnpm install --frozen-lockfile && pnpm exec playwright install chromium
```

## Steps
1. Ensure deps are installed.
2. **PROBE first on a new env** (cheap: builds ONE page with the first 3 types, generates them,
   dumps every API shape + the generation-status progression):
   ```
   cd ~/myqa-output && PROBE=1 node ~/.hermes/skills/qa-asset-zoo/scripts/build-asset-zoo.mjs staging
   ```
   Read `~/myqa-output/smoke-screens/staging/asset-zoo/probe.json`. Confirm: instance/workspace +
   API host resolved, asset-config fetched, blank chat created, a page was created, adds
   returned ok, and each asset reached `generation_status: completed` (watch the "waiting…" log
   lines), and the learner page rendered. Fix the script if any step failed before the full
   build.
3. **Full build** (all batch types, 5/page, writes the manifest):
   ```
   cd ~/myqa-output && node ~/.hermes/skills/qa-asset-zoo/scripts/build-asset-zoo.mjs staging
   ```
   (Use `local` or `prod` instead of `staging`.) Generation can take several minutes — the
   script polls until every asset is `completed`/`failed` (or a long timeout).
4. Read the manifest `~/.hermes/asset-zoo-<env>.json` (copy under `~/myqa-output/smoke-screens/<env>/asset-zoo/manifest.json`): `pages`, `assets:[{type, asset_id, page_id, generation_status, ai, learner_url}]`, `missing_types`, `failed_generation`, `add_results`. Combine with exit code (0 = ok, 1 = failed, 2 = setup).

## Report
`RESULT: PASS` or `RESULT: FAIL` on the first line, then:
- environment; fixture course title and `hub_id`; topic; how many types requested vs on the page
- `generation_status` per type (how many `completed`, and which `failed` — from `failed_generation`)
- types that never appeared (`missing_types`) — absent from the manifest
- the manifest path; side effects: a `[SMOKE] Asset Zoo` course was created (left as the fixture), AI credits were used

**PASS** if any of:
- exit 0 and the manifest lists assets with `generation_status: completed`

**FAIL** if any of:
- exit 1 (report the failing stage and any `failed_generation`)
- exit 2 (setup)
